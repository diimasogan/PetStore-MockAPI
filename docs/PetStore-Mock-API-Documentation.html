Executive summary

PetStore Mock API is a small Boomi Web Services project that mimics two operations of the public Swagger Petstore: get a pet by ID and create a pet. It gives front-end and integration teams a stable endpoint to build against before the real back end exists.

It is also a clean reference for the layering used in larger projects: a thin listener process, a sub-process with the business logic, a JSON profile for the contract, and Petstore-style error responses.

Responses

CaseHTTPBody
GET with a numeric petId200Mock Pet “doggie” with the requested id
GET with a missing or non-numeric petId200{"code": 400, "type": "error", "message": "Invalid ID supplied"}
POST with a name200The request body, echoed back
POST without a usable name200{"code": 405, "type": "error", "message": "Invalid input: pet name is required"}
Note: the processes do not set an HTTP status, so the listener answers 200 even for errors. Clients should check type == "error" in the body.

Process design

ProcessShapesLogic
PetStore API - Get PetStart (WSS Listen: PetStore WSS Get Pet) → Process Call → Return DocumentsReceives GET, passes the request to the sub-process.
[SUB] PetStore Get PetStart (passthrough) → Decision “Valid Pet ID?” → Message → Return Documentsquery_petId matches ^[0-9]+$ → mock Pet with that id; otherwise ApiResponse 400.
PetStore API - Create PetStart (WSS Listen: PetStore WSS Create Pet) → Process Call → Return DocumentsReceives the JSON body, passes it to the sub-process.
[SUB] PetStore Create PetStart (passthrough) → Decision “Pet Name Provided?” → Notify / Message → Return Documentsname matches .*\S.* → Notify “Pet accepted: {1}” and echo the body; otherwise ApiResponse 405.

Design decisions

  • Thin listener, testable logic. The [SUB] processes use a passthrough start, so they can be run in Test Mode with a sample document — no HTTP call needed.
  • Regex decisions keep validation explicit and visible on the canvas.
  • Message shapes produce the exact Petstore JSON, so clients written for Swagger Petstore work unchanged.
  • No persistence on purpose: the mock is stateless and safe to call repeatedly.

  • docs/ — this documentation (source in docs/_source/).

Setup & deployment

  1. Copy .env.example to .env and fill in the Boomi account, API token, target folder, environment and test atom.
  2. Push the components in active-development/ to the platform folder.
  3. Deploy PetStore API - Get Pet and PetStore API - Create Pet to an Atom Cloud environment with the shared web server enabled.
  4. Call the endpoints with the shared web server user (Basic auth) and run the test cases above.

Limitations & next steps

Static GET data

GET always returns “doggie”; created pets are not stored.

HTTP status codes

Set the HTTP status (400/405) through the response headers so clients don’t need to inspect the body.

Persistence

Store pets in a database or Disk V2 and look them up by id.

More operations

Add PUT /pet, DELETE /pet/{petId} and findByStatus.

API Management

Publish through a Boomi API Service component with an OpenAPI spec.

Schema validation

Validate status against available | pending | sold and the types of every field.
